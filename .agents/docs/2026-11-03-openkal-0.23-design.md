# openkal 0.23：映像在其基址上放置

2026-11-03。状态：**实施所依据的方案**。规范对照基于 `SPEC.md` 0.22，结果为 0.23.0。
来源：mcpp 生态设计 2026-11-02 part 3 §16.8、§17.6；mcppls-clangd #16 的 warm-prime（Linux x64、macOS arm64）。

---

## 1. 要解决的问题

warm-prime 的冷阶段启动 176 个 worker。CI 的 Linux x64 上映像的处理器时间为原生的 1.27 倍、缺页为 1.42 倍，macOS arm64
的缺页为 2.32 倍；本机（Linux x64）为 1.09 倍。差距按 worker 平均分摊，与模块大小无关：

| # | 测量 | 结果 |
| --- | --- | --- |
| P1 | 一次启动（`--version`）的缺页 | 原生 297（非 PIE，固定地址），映像 1285 |
| P2 | 映像的重定位 | `.rela.dyn` 3.9 MB，约 164 000 条相对重定位，落在 2 MB 的 `.data.rel.ro` 上 |
| P3 | 打包的相对重定位（`-z pack-relative-relocs`） | 表缩为 32 KiB，缺页 1285 → 1160；可写段仍被整体复制并逐项改写 |
| P4 | 每次多出的缺页的代价 | 本机每个 worker 约 3.5 ms，CI 的 x64 虚拟机约 24 ms |

映像是位置无关的（12.2），加载器每次启动都要写入相对重定位算出的每个地址；为一个地址链接的原生程序不写这些地址，其只读
数据是文件的页，按需缺页并预读相邻页。

## 2. 增补

| 接口 | 增补 | 层级 | 条文 |
| --- | --- | --- | --- |
| `openkal.exec` | `kal_exec_alloc_at(at, size)`、属性 `KAL_EXEC_PROP_PLACE` | 属性位 | 11 条 48、12.3 |
| 映像格式 | 第 3 类 note（placement）：基址与各个在文件中有字节的可写段（按地址升序）按该基址算好的字节在文件中的位置；本条文版本 1.1 | 可选 note | 12.4 |
| 加载器 | 得到基址时，只读部分（`PT_GNU_RELRO`）中没有符号重定位的粒度直接映射文件的字节，其余复制，只做引用符号的重定位 | 陈述 | 12.3 |
| `openkal.fs` | `kal_fs_resolved_name(base, name, len, out, cap)`、属性 `KAL_FS_PROP_RESOLVED_NAME` | 卷的属性位 | 11 条 49 |

`kal_exec_alloc_at` 在 `at` 处预留区域，该处已有内容或环境不允许程序选择地址时返回空指针、不预留任何东西；`at` 是
`kal_memory_granularity` 的倍数。

同一次测量（warm-prime 的已有缓存阶段，`strace -c`）中，映像发出 87 万次 `newfstatat`，原生为 35 万次 `stat` 与 10 万次
`readlink`：映像的 `realpath` 逐个组成部分询问是否为链接（`usr`、`usr/lib`、`usr/lib/gcc`……），原生程序对打开的每个文件只问
环境一次（Linux 的 `/proc/self/fd`，macOS 的 `F_GETPATH`）。CI 的 x64 上映像的内核态时间因此多 20%。`kal_fs_resolved_name`
回答名字跟随全部链接后的绝对名字：Linux 以 `O_PATH` 打开后读 `/proc/self/fd/N`，macOS 以 `O_EVTONLY` 打开后取 `F_GETPATH`，
Windows 以 `GetFinalPathNameByHandleW`；openkal-musl 的 `realpath` 先用它，卷不声明时照旧逐个询问。

## 3. 方案中的决定

1. **一个操作，而不是 `kal_exec_alloc` 的提示。** 加载器在写入任何东西之前就要知道是否拿到了基址：拿到时取存储的字节，拿不到
   时按文件重定位。提示得到的地址需要再比较，比较之后的回退正是这个操作的语义，所以由操作陈述。
2. **属性位，而不是必需。** 有的环境替程序决定每块内存的位置。Linux 用 `MAP_FIXED_NOREPLACE`（4.17 之前的内核把它当作
   提示，结果不同则释放并拒绝），macOS 用提示并比较（`MAP_FIXED` 会替换已有内容），Windows 用 `VirtualAlloc` 在该地址预留；
   三个实现都声明该位。Windows 不声明 `KAL_EXEC_PROP_FILE`，得到基址时复制存储的字节，省去重定位但不省去复制。
3. **基址由映像决定，在封装时选定。** 同一映像的所有进程放在同一地址，重定位后的只读数据在各进程中相同，可以是同一文件的页。
   基址取自映像内容的摘要，落在用户地址空间的中段（16 TiB 起，4 GiB 一档），与系统分配器自上而下的放置相距很远；一个进程中
   多个映像各有其基址，冲突时后者照常重定位。
4. **只存可写段，只跳过相对重定位。** 指令与只读数据本来就是文件的字节（0.21）；引用符号的重定位指向加载器绑定的实现入口，
   因加载器而异，仍在加载时完成。只读部分（`PT_GNU_RELRO`）中没有这类重定位的粒度不再被写，可以映射文件；其余粒度复制后
   改写。
5. **格式版本 1.1。** 新 note 是可选的；1.0 的加载器不读它，照常重定位，行为不变。一个要求新加载器才能运行的映像不由此产生。
6. **先放置，后签名。** 签名覆盖整个文件（12.4 第 2 类），存储的段也在其中；`okld place` 拒绝已签名的映像。基址取自 ELF
   所描述的字节（placement 描述符读作零），同一映像无论放置几次都得到同一基址与同一字节。

## 5. 验证

- 一致性套件：未对齐的地址被拒绝；已有区域的地址被拒绝且原区域不变；刚释放的地址被重新预留并可写；未声明该位的实现拒绝
  所有请求。openkal-linux 0.24 的本地一致性：328 项全部成立。
- openkal-image：同一映像在基址上、在任意地址上（`OKRUN_PLACE=0`）与未放置时观察到的内存相同；在基址上不做相对重定位；
  封装后的映像通过 `okld check`，存储段的一个字节被改动时被拒绝；重复放置不改变字节；openkal-image 0.3.1 的 okrun 照常运行
  0.4.0 封装的映像。本机（Linux x64）clangd 映像一次启动（`--version`）的缺页：在基址上 606，在任意地址上 1 047；
  `PT_GNU_RELRO` 的 2 MB 中除首尾两个 64 KiB 外都是文件的页。
- warm-prime：CI 的 Linux x64、arm64、macOS arm64 上映像对原生的冷阶段处理器时间与缺页。
