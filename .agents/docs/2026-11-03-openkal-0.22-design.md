# openkal 0.22：位置上的空设备

2026-11-03。状态：**实施所依据的方案**。规范对照基于 `SPEC.md` 0.21，结果为 0.22.0。
来源：mcpp 生态设计 2026-11-02 part 3（ok 映像的性能对等）§16.7、§17.5；mcppls-clangd #16 的 warm-prime 与 mcppls #75 的
Windows 端到端测试。

---

## 1. 要解决的问题

clangd 作为 ok 映像在 Windows 上为每个模块启动 worker，全部失败：`failed to launch module worker: posix_spawn failed: No such
file or directory`。

| # | 现象 | 原因 |
| --- | --- | --- |
| N1 | 映像中 `open("/dev/null")` 为 `ENOENT`，Linux 上同一映像成功 | openkal-musl 按 preopen 解析名字；Windows 的 preopen 是卷（`C:/`…），没有名为 `/` 的目录 |
| N2 | `posix_spawn` 在加入 `addopen(…, "/dev/null", …)` 后为 `ENOENT` | LLVM 的 `ExecuteNoWait` 把空路径的重定向写成 `/dev/null`；worker 的标准输入与输出都是空重定向 |

空设备是每个启动程序的环境都有的资源，各自以自己的写法命名：Linux、macOS 为 `/dev/null`，Windows 为 `NUL`。openkal 不命名
它所提供的目录之外的任何东西，程序无法经由本接口按名字到达它。

## 2. 两层的分工

| 用法 | 所需 | 归属 |
| --- | --- | --- |
| 程序自己读写空设备 | 读得到输入结束、写全部接受：纯语义，无需环境的对象 | C 库（openkal-musl 0.27） |
| 把空设备交给启动的程序 | 启动的程序在该位置持有一个环境的句柄；它可能不是 openkal 程序 | openkal（本版本） |

C 库可以用已有的接口拼出第二种用法：输入给一个远端已释放的通道，输出给一个由调用者的任务持续读空的通道。这一拼法与空设备
不等价：调用者先结束时，启动的程序的写入以错误结束（Linux 上默认被 SIGPIPE 结束）；每个字节经过管道并由调用者复制；每个程序
的每个位置占用调用者的一个任务；启动的程序看到的是管道而不是字符设备。mcpplibs.os 0.2.7 的 `stdio::null` 正是这样拼出的，并
以 `host() != windows` 选择路径，即在 openkal 之上的库里按系统名改变调用方式。

## 3. 增补

| 接口 | 增补 | 层级 | 条文 |
| --- | --- | --- | --- |
| `openkal.process` | `KAL_SPAWN_NULL_IN`、`KAL_SPAWN_NULL_OUT`、`KAL_SPAWN_NULL_ERR`；属性 `KAL_PROCESS_PROP_NULL_STREAMS` | 属性位 | 7.15、11 条 47 |

位置上的标志使该位置得到环境的空设备：启动的程序在该位置读到输入结束，写入全部接受并丢弃。未声明属性位的实现报告
`kal_err_not_supported` 且不启动程序；同一位置上标志与非零的流同时出现为 `kal_err_invalid`。

## 4. 方案中的决定

1. **启动的标志，而不是一个流。** 返回一个空设备流的操作需要与之配套的释放（`openkal.stream` 没有释放，通道的释放是
   `kal_process_channel_close`），且程序自己读写空设备时 C 库无需环境即可回答；需要环境的只有交给启动的程序这一种用法，它属于
   启动。`kal_spawn` 的布局不变（`flags` 已有），`SURFACE.txt` 不增加名字，加载器（okrun）的绑定表不变。
2. **三个位置各一个标志。** 三个位置互相独立，C 库的文件动作逐个位置给出；一个"全部为空"的标志无法表达"输入为空、输出为管道"。
3. **属性位，而不是必需。** 不启动程序的环境（openkal-emscripten、openkal-opensbi）没有可交付的对象；声明 `openkal.process`
   的三个实现都声明该位。
4. **设备在启动的程序一侧打开。** Linux、macOS 的实现在替换前的映像（复制体）中打开 `/dev/null` 并放到位置上，调用者不持有其
   描述符；Windows 的实现为本次启动打开 `NUL`，按调用者的流的方式标记为可继承并列入 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`，
   启动后释放。7.13（启动的程序只得到三个流与授予的目录）不变。
5. **名字留在 C 库。** openkal-musl 把 POSIX 的 `/dev/null` 解析为进程内的空描述符，并在 `posix_spawn` 的文件动作中把它映射为
   相应位置的标志；`NUL` 这一写法只出现在 openkal-windows 中。

## 6. 验证

- 一致性套件：声明该位的实现，启动的副本在三个位置得到空设备时读到输入结束、写入全部接受（状态 60）；标志与非零的流同处一个
  位置为 `kal_err_invalid`；未声明该位的实现拒绝该标志；能力字只含规范分配的位置。openkal-linux 0.23 的本地一致性：324 项全部成立。
- 实现自己的测试：启动的程序在该位置看到字符设备（Linux、macOS 为 `fstat` 的 `S_IFCHR`，Windows 为 `GetFileType` 的
  `FILE_TYPE_CHAR`），读到输入结束，写入被接受；启动前后调用者的描述符或句柄数相同。Windows 的测试在 Wine 下通过。
