# openkal 0.20：按偏移的传输、单元的用量与限额、内存区域、观测

2026-11-02。状态：**实施所依据的方案**。规范对照基于 `SPEC.md` 0.19，结果为 0.20.0。
来源：mcpp 生态设计 2026-11-02 part 3（ok 映像的性能对等）§5、§6，评审 §16。

## 1. 要解决的问题

clangd 以 ok 映像运行时，同一份引擎比原生多用 1.6 倍以上的 CPU，缺页多两个数量级（part 3 §2.2）。归因中属于 openkal 一层的有四项：

| # | 现象 | 缺的东西 |
| --- | --- | --- |
| R1 | 分配器的组来自 `kal_alloc`，空组即整块归还，再用时重新缺页、清零（792 k 缺页，原生 55 k） | 保留与提交分开的地址区间 |
| R3 | `pread` 由 C 库拼成"定位、读、定位回"，持锁（66 k 读 + 71 k 定位 + 73 k 让出） | 一次调用、不动位置的传输 |
| — | clangd 的 worker 组内存预算只在 Linux 上以 cgroup 实现 | 单元的用量与限额 |
| — | 映像在 perf 中是匿名映射；C 库各层做了什么无从得知 | 程序向测量者陈述计数；地址的名字 |

## 3. 实施中对 part 3 方案的修正

1. **内存区域是独立的可选接口，不是 `openkal.memory` 的操作。** part 3 §5.3 写作 `kal_memory_*` 加属性位。`openkal.memory`
   属于 core（3.2），没有页表的环境只能导出总是失败的桩，这正是 6.1 所说的缺陷；按 6.2，"实现可能缺少的操作自成一个接口"。
   操作与语义不变。
2. **单元的用量不报告峰值。** 只有一个环境（cgroup 的 `memory.peak`、作业对象的峰值）记录单元的峰值；其他环境要报告就得记住
   每个被问过的单元（7.1）。调用者需要峰值时在关心的时刻询问并保留最大值。单个程序的峰值保留（三个环境都记录）。
3. **结束的程序的用量在句柄释放之前可读。** `kal_process_wait` 之后、`kal_process_close` 之前，`KAL_PINFO_MEMORY` 给出峰值——
   这正是 C 库 `wait4` 的 `ru_maxrss` 所需。Linux 因此改为 `kal_process_wait` 只等待不回收（`waitid(WNOWAIT)`），
   `kal_process_close` 回收。
4. **Windows 的按偏移传输经第二个句柄。** 同步句柄上带偏移的 `ReadFile` 会移动位置；part 3 写的"自存位置"会让位置不再与
   子程序共享（重定向给子程序的文件）。改为首次需要时以同一文件打开第二个句柄（只用于按偏移传输，其位置无人观察），
   主句柄的位置仍是环境的。
5. **Linux 的限额只声明 SUPERVISED。** cgroup 只能建在被委派的子树中，而"是否委派"是服务管理器的记录，不是内核的；
   普通桌面上程序自己的 slice 可写但未委派。实现若在可写处建组即越权。持有委派、需要内核上限的程序直接使用它
   （1.1：越过 openkal 的程序自负其责）。HARD 由 Windows（作业对象）实现。
6. **`openkal.prof` 不含周期计数器。** 它会是 `kal_time_monotonic` 之外的第二个时基。
7. **`openkal.debug` 只命名地址，不回溯栈帧。** 程序以自身的展开表回溯（12.2），缺的只是映像文件中的符号表。

## 4. 验证

- 一致性套件：`fs` 增加按偏移传输（位置不变、顺序传输随后从原位置继续、读到末尾与之外、写过末尾补零）；`process` 增加程序的
  内存、单元用量、限额结束整个单元并报告 `KAL_TERMINATED_LIMIT`、结束程序的峰值在释放前可读；新节 `region`、`prof`、`debug`。
- 各实现自己的测试：openkal-linux 的 4 个上下文并发按偏移读与一个顺序读者、vDSO 时钟单调；openkal-musl 的 L1 基准（part 3 §11）。
