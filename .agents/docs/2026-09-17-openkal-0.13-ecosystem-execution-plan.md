# openkal 0.13 生态执行计划：任务拆分、依赖与发布顺序

- 日期：2026-09-17
- 依据：`2026-09-17-openkal-ecosystem-cross-repo-design.md`（含 §9、§10 的 review 结论：R1、R3 采纳）
- 同时吸收：`openkal-musl/.agents/docs/2026-09-04-issue28-item3-start-failure-and-error-vocabulary.md`
- 约定：每个仓库一个 PR，分支名统一为 `openkal-0.13`。各仓库 CI 按同名分支取兄弟仓库的工作树，发布之前就能完成跨仓库验证。文档和代码注释不使用表情符号。

## 1. 对设计稿的三处修正（执行前确定）

1. **错误值命名为 `kal_err_not_program`，不用 `kal_err_not_executable`。** 09-04 的分析已经说明：`executable` 容易被读成权限位，而这个值表达的是"名字存在，但不是这个环境能够启动的形式"。它和 `kal_err_not_directory` 同形。K1 的谓词仍叫 `executable`，因为它描述的正是卷上记录的可执行性。
2. **openkal-macos 有一个既存缺陷，并入本轮。** 启动一个起不来的名字（包括不存在的名字）时，它返回 `kal_ok` 和一个句柄（`src/process.cpp` 在 `execve` 之后执行 `exit(127)`，父进程没有报告通道）。修法是移植 openkal-linux 的 exec 报告管道；conformance 增加一条可移植的观察，并且修复前必须为红。
3. **openkal-linux 流句柄避开 0（#28.2）本轮不做。** 规范允许但不要求这样做；openkal-musl 已经显式拒绝有歧义的放置，不存在静默错误。改变所有流句柄的编码风险大于收益，所以在 SPEC §11 中记录为已考虑、暂不定义。

## 3. 任务与依赖

```
 T0  计划（本文）
 T1  openkal 规范 0.13（头文件、SPEC、SURFACE、conformance、K5 文档）   <- 所有实现依赖它
 T2  openkal-linux      依赖 T1
 T3  openkal-macos      依赖 T1
 T4  openkal-windows    依赖 T1（句柄继承与 overlapped socket 不依赖）
 T5  openkal-emscripten / opensbi / uefi / alloc-kal 重新钉住   依赖 T1
 T6  openkal-musl       依赖 T1，并通过同名分支取 T2/T3/T4 的工作树验证
 T7  openkal-llvm-runtime   依赖 T6
 T8  mcpp #662（M1–M4、D4、M5）   独立
 T9  tinyhttps          依赖 T8 发布（封闭构建下才能验证 musl 路径）
 T10 mcpp-index         依赖 T1–T9 全部发布
 T11 发布：GitHub 标签 + GitCode 资源（gtc）+ xim-pkgindex 上的 mcpp 升级 PR
 T12 验证：xlings subos 沙箱 + CN 镜像，端到端解析已发布的版本
 T13 自我审查（逐仓库，外加生态级审查）；K6：回复并关闭 issue
```

可以并行的组：{T1, T4 的非规范部分, T8}，然后 {T2, T3, T4, T5}，然后 T6 → T7，同时 T9 → T10。

## 4. 各任务的验收判据

| 任务 | 判据 |
| --- | --- |
| T1 | `tools/check-declarations.sh`、类型检查、conformance 可以编译；新观察在旧实现上为红（至少 macOS 的启动报告那一条，以及 K1、K2 的缺失） |
| T2/T3/T4 | 各自 CI：conformance 全部 held、surface、independence；新增测试覆盖 K1、K2（T4 另外覆盖句柄继承和全双工） |
| T6 | `examples/subprocess` 等 probe 在四个 CI 行上断言：`posix_spawn` 启动非程序文件返回 `ENOEXEC`；`chmod +x` 往返；`chmod(0600)` 返回 `ENOSYS`；`stat` 报告 x 位 |
| T8 | 单元测试覆盖选项矩阵，且原生构建的命令行逐字节不变；e2e 在宿主装有 mingw 的 shard 上断言搜索列表只含 store 路径与 resource 目录，修复前为红 |
| T9 | openkal Windows 交叉构建通过 |
| T10 | validate CI 全绿；兼容测试 workflow 在 Linux 上产出结果文件；站点可以构建 |
| T12 | 沙箱中只写版本号，就能解析并构建 openkal 可移植示例、zlib 成员和 tinyhttps 成员 |

## 5. 风险

- **磁盘**：剩余约 41G。LLVM runtime 和 musl 的构建占用大，需要时清理旧的 `target/` 和已不用的 subos。
- **没有本地 macOS**：T3 的运行时验证只能在 CI 上完成；本地只做交叉编译。
- **精确版本钉住**：任何一个包漏掉都会得到 `irreconcilable versions`。重新钉住的清单按"反向扫描索引"得出，不从改动点外推。
